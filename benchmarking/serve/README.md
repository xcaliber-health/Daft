# Query server benchmark suite

Head-to-head comparison of four execution lanes over the same Iceberg
tables:

| lane | engine | topology |
|---|---|---|
| `daft-inprocess` | Daft native (Swordfish) | in-process |
| `daft-serve` | Daft native behind `daft-serve` | client-server |
| `duckdb-inprocess` | DuckDB + iceberg extension | in-process |
| `duckdb-quack` | DuckDB behind a Quack server | client-server |

Daft lanes run the DataFrame TPC-H programs from `benchmarking/tpch/answers.py`;
DuckDB lanes run the stock TPC-H SQL from its `tpch` extension. Data is
generated by DuckDB `dbgen` and written through PyIceberg (engine-neutral).

## Quick start (local, no containers)

```bash
# Smoke: SF 0.01, all four lanes, correctness gate + timings
python -m benchmarking.serve.bench --warehouse /tmp/tpch-sf001 --scale-factor 0.01

# Real numbers: SF 1 or 10, more iterations, record a baseline
python -m benchmarking.serve.bench --warehouse /tmp/tpch-sf1 \
    --scale-factor 1 --iterations 5 --record-baseline

# Concurrency: closed-loop clients against both server lanes
python -m benchmarking.serve.concurrency --warehouse /tmp/tpch-sf001 \
    --clients 1 4 16 --duration-secs 30
```

`bench` exits non-zero on any correctness mismatch between lanes or a >15%
p50 regression against a recorded baseline (`baselines/sf<sf>.json`), and
writes `report.md` beside this file.

## Containerized environment (compute near data)

For runs where the client has no storage access and data lives behind an
object store + REST catalog:

```bash
docker build -f deploy/Dockerfile.serve -t daft-serve:dev .
docker compose -f benchmarking/serve/docker-compose.yml up -d
# Load data through the REST catalog (uses the same generator):
#   point PyIceberg at http://localhost:8181 / s3://warehouse (minio creds)
# Then benchmark the daft-serve lane against the container:
python -m benchmarking.serve.bench --warehouse /tmp/tpch-sf1 \
    --lanes daft-serve --serve-address daft://localhost:9494 --serve-token bench
```

## Methodology

> **Build the optimized engine first: `make build-release`.**
> `make build` produces a debug (opt-level 0) extension whose engine-side
> timings are 3-30x slower than release; benchmarks taken with it are
> meaningless as absolutes and unfair against release-built engines.

- Iteration order is query-major (`for query: for lane:`) so every lane sees
  the same page-cache and module-import state for a given query; no lane
  systematically pays all cold-start costs.
- `--warmup N` (default 1) runs and discards N iterations per (lane, query)
  before timing; the first is reported separately in the report's
  "Cold start" table. Timing percentiles cover warm iterations only
  (`--iterations`, default 5).

## Native A/B regression check

To prove a branch introduces no native-engine regression, benchmark the
`daft-inprocess` lane on the parent commit and compare the branch against
that baseline:

```bash
# 1. Build the parent commit in a separate worktree.
git worktree add ../daft-parent <parent-sha>
(cd ../daft-parent && make .venv && make build)

# 2. Record the parent baseline (native lane only).
(cd ../daft-parent && python -m benchmarking.serve.bench \
    --warehouse /tmp/tpch-sf1 --scale-factor 1 \
    --lanes daft-inprocess --record-baseline)

# 3. Copy the baseline into this tree and run the branch against it.
cp ../daft-parent/benchmarking/serve/baselines/sf1.0.json benchmarking/serve/baselines/
python -m benchmarking.serve.bench --warehouse /tmp/tpch-sf1 \
    --scale-factor 1 --lanes daft-inprocess --skip-datagen
```

A non-zero exit flags any query whose warm p50 regressed more than 15%.

## Notes

- The `duckdb-quack` lane requires the `quack` core extension (DuckDB
  ≥ 1.5.3, beta). If it cannot start, it is reported unavailable and other
  lanes still run — results stay honestly labeled.
- Daft lanes ship the *unoptimized* plan to the server; scan planning and
  pruning run server-side. With a local `SqlCatalog` warehouse, table
  handles cannot travel, so the client falls back to materializing scan
  tasks locally; the REST-catalog environment exercises the fully lazy path.
